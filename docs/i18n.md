# Internationalization

The Desktop Renderer ships in English and Simplified Chinese. The `workbench.language` setting
(Settings › General › Language) selects one; its default, `null`, follows the system language: any
Chinese system preference renders Simplified Chinese, every other language renders English. Changing
the setting re-renders the open windows immediately, with no reload. The mobile app ships the same two
languages and follows the phone's system language (see [Mobile](#mobile)).

## Runtime

The runtime is [`@lobehub/ui`'s i18n](https://ui.lobehub.com/components/i18n), wrapped by
`apps/desktop/src/renderer/src/i18n/`, the only Renderer module allowed to import the
library (an accepted exception recorded in the stack baseline; ESLint enforces it):

- `useLocaleStore` is the single source of the active locale. `I18nProvider` renders the library's
  `ConfigProvider` with that locale and its flat dictionary. It deliberately does not use the library's `I18nProvider` export: that component
  always installs a global focus ring that overrides every focus-visible outline with `!important`.
  `ConfigProvider` owns the same i18n context and accepts `globalFocusRing: false`.
- `syncWorkbenchLocale()` (`stores/workbench-locale.ts`) subscribes to the Workbench store in the
  Workbench, Caxri Bot, and Benchmark windows and applies the setting synchronously, inside the snapshot
  write and before React renders it. A provider effect would update the store one render late, so
  `translate()` calls made during the switching render would still return the previous language.
  Process Explorer and Performance Monitor have no Workbench snapshot, so Main passes its resolved `workbench.language` locale on the window's
  entry URL (`caxri-locale`) and the window opens in the Workbench's language; it keeps that language until reopened.
- `useTranslation()` returns a typed `t(key, parameters?)` for components. It reads the library
  context, so a language change re-renders every consumer.
- `translate(key, parameters?)` serves code outside React: stores, command handlers, toasts raised
  from events. It reads `useLocaleStore`. Its
  result is a snapshot. Never call it at module top level, and never call it during render where
  `useTranslation()` is available. The React Compiler memoizes render output by its inputs and the
  locale is not one of them, so a render-time `translate()` keeps the old language after a runtime
  switch. Helpers called from render therefore take `t` as a parameter, and cached or serialized
  data stores `TranslationKey`s (or the raw error) instead of translated strings, and the text is
  produced at render with the current `t`. `caxri/no-render-translate` flags a direct `translate`
  use inside a component, hook, or `useMemo`/array callback; it cannot follow a call into a helper,
  so helpers take `t: Translate` as a required parameter and the same rule forbids a `t = translate`
  or `x.t ?? translate` fallback, which would let a caller that forgets `t` silently render the old
  language. Event handlers, stores, and other non-render entry points pass `translate` explicitly.
- `t.locale` is the locale `t` translates into (`useTranslation()` returns it, and the module-level
  `translate.locale` reads the store). Number and date formatters in `lib/locale-format.ts` take the
  locale as a required argument and never read the store, so a helper that already receives `t`
  formats with `t.locale` and a component with `useTranslation().locale`. A formatter that read the
  global locale would keep the old language after a runtime switch for the same memoization reason.

Main translates its own native UI (the menu bar, message boxes, and file dialog titles) through
`apps/desktop/src/main/locale.ts`. Its dictionaries are the shared `commands` namespace plus the
Main-only `desktop` namespace in `apps/desktop/src/shared/i18n/`. Every native menu refresh reads
`workbench.language` together with the keybindings and resolves `null` against
`app.getLocale()`, Chromium's locale, which honors `--lang` like the Renderer does; `settings.changed` triggers that refresh, so the menu bar
rebuilds in the new language. Dialogs translate when they open. `translateMain()` reads module state, so the prompt builders stay plain
functions that Vitest imports without Electron.

The library's own built-in strings (`common.cancel`, `common.confirm`, `common.delete`,
`common.edit`, `common.clear`, `common.empty`, and the `form.*`, `hotkey.*`, `image.*` groups) are
merged into the same dictionaries and are valid keys. Caxri resources must not redefine them; the
i18n unit test rejects an overlap.

## Resources

`i18n/locales/en/<namespace>.ts` holds the English source strings, one module per Renderer feature
(`agent-chat.ts` exports `agentChat`), plus:

| Namespace  | Owns                                                                         |
| ---------- | ---------------------------------------------------------------------------- |
| `common`   | Generic single words reused across features (Close, Retry, Save, ...)        |
| `core`     | Shared chrome outside `features/`: `components/`, `hooks/`, `lib/`, `stores` |
| `commands` | Command titles and categories, in `apps/desktop/src/shared/i18n/`            |
| `desktop`  | Main-only native menu and dialog copy, in `apps/desktop/src/shared/i18n/`    |
| `settings` | Settings categories, rows, and the protocol settings catalog                 |

The `commands` namespace lives in `apps/desktop/src/shared/i18n/{en,zh-cn}/` because Main's native
menu shows the same titles; the Renderer aggregates import it from there.

`i18n/locales/zh-cn/<namespace>.ts` mirrors each module and is typed
`TranslatedNamespace<typeof source>`, so a missing, extra, or misspelled key fails type checking.
The unit test additionally checks that every translation is non-empty and keeps the same
`{{placeholders}}` as its English source.

Keys are flat strings, `<namespace>.<camelCase path>`, for example
`agentChat.composer.placeholder`. Choose keys by meaning, not by English wording, so a copy edit does
not force a rename. Placeholders use `{{name}}`. There is no plural engine: choose between `...One` and
`...Other` keys in code when English needs different forms (Chinese can repeat the same text).

### Strings owned by the protocol catalogs

The command catalog and the settings catalog in `@caxri/protocol` keep their English `title`,
`description`, and option labels. They remain the source of search keywords, the CLI, and the
native menu. The Renderer translates them at display time through keys derived from the stable id,
such as `` `commands.${id}` `` or `` `settings.${key}.title` ``. A template literal over the id union
type-checks against `TranslationKey` only when every id has an entry, so a new command or setting
fails type checking until it is translated.

Most Agent Chat copy has one implementation: the protocol helper takes a `t` and reads the shared
catalog described below. A few helpers in `@caxri/protocol` still produce English copy for the phone
and the CLI while Desktop renders its own localized counterpart (tracker card lines and Git diff tab
labels). Under the English locale both must agree byte for byte. Every such Desktop counterpart
registers a row in `apps/desktop/src/renderer/src/i18n/__tests__/english-counterpart-parity.test.ts`,
which feeds both sides inputs that reach every branch, so a wording or rule change on one side fails
there instead of silently diverging. Moving a counterpart onto the shared catalog removes its row.

The placeholder title of an unnamed Session (`DEFAULT_SESSION_TITLE`, `Untitled`) is Server data shared with the CLI and
mobile, so it stays English in storage. Renderer surfaces show it through `sessionTitleForDisplay`
(`features/session/session-title.ts`), and the phone through its own `sessionTitleForDisplay`
(`apps/mobile/src/features/sessions/session-row-model.ts`); matching, sorting, and rename requests
keep the stored title.

### Agent Chat labels shared by Desktop and mobile

The words Agent Chat derives from its records (work rows, turn folds, the activity line, request
cards, failure banners, diff kinds, permission levels, reasoning effort levels, and Bot Inbox
kinds) live in one
protocol catalog: `packages/protocol/src/agent/agent-chat-labels-en.ts` with its typed
`agent-chat-labels-zh-cn.ts`. Desktop's and mobile's `locales/{en,zh-cn}/index.ts` spread these
catalogs, so the keys (`agentChat.tool.*`, `agentChat.fold.*`, and so on) resolve through either
app's `t`. The presentation helpers that build these labels (`describeAgentChatWork`,
`agentChatTurnLabel`, `agentChatActivity`, `agentChatFailureMessage`, and the rest) live in
`@caxri/protocol` and take `t: AgentChatLabelTranslate` as their last parameter, defaulting to
English; each app passes its own `t`. Records that travel over the wire, such as the English tool
label from `describeAgentTool`, stay English; `agentToolLabel(label, t)` translates one at display
time.

### Strings owned by bundled extensions

The bundled Git and Status extensions localize their own copy through the Extension API, the same way a third-party
extension would; see [Extension localization](extensions.md#localization). Their manifest titles resolve from
`package.nls.json` and `package.nls.zh-cn.json`, and every runtime string goes through `l10n.t` with its translation in
`l10n/bundle.l10n.zh-cn.json`, keyed by the English message. The Renderer receives display-ready text and does not
translate extension copy; only the Workbench Core containers (Files, Info, Logs) stay keyed by id in
`view-container-labels.ts`.

When you add or reword a user-visible string in `extensions/git` or `extensions/status`, edit its bundle entry in the
same change. `scripts/__tests__/extension-l10n-bundles.test.ts` fails on a message without a translation, a translation whose
message no longer exists, or mismatched placeholders. Write each plural form as its own full message rather than
concatenating fragments, so the translation can reorder words.

Server-composed recovery sentences follow the other rule: the Server sends a closed reason enum (plus a deadline) and
the Renderer owns the copy, as `pullRequestUnavailableHint` does for a failed pull request lookup. The Project Status
errors the Server still composes in English (`projectStatusCliError`: not installed, not signed in, rate limited, and the
rest) are recognized by the Status extension in `status-server-text.ts` and rendered through its bundle, until the
Server sends structured reasons (#1865). The Agent prompts the panel sends stay English: they are written for the
Agent, not the reader. The fallback Agent name (`Unknown Agent`) is a getter on `agentIconRegistry` that reads the active
language when a surface asks for it.

## Mobile

The mobile app (`apps/mobile/src/i18n/`) follows the phone's system language with Desktop's rule
(`resolveAppLocale` from `@caxri/protocol`): any Chinese preference renders Simplified Chinese, every
other language renders English. It has no language setting of its own and does not read
`workbench.language`, because the phone pairs with Desktops that can each choose differently.

- `locale-store.ts` holds the active locale. Hermes resolves `Intl` against the Android or iOS
  system locale, so `syncSystemLocale()` reads it without a native module. The root layout calls it
  before the first screen paints and again whenever the app returns to the foreground, since the
  reader may change the system language while Caxri is in the background.
- `useTranslation()` returns `{ locale, t }` through `useSyncExternalStore`; `t` changes identity
  with the locale, so memoized values that depend on it recompute. `translate()` serves non-React
  modules, which take `t: Translate = translate` as their last parameter so React callers pass their
  `t` and tests stay deterministic in English.
- Resources follow the Desktop layout: `locales/en/<namespace>.ts` is the English source,
  `locales/zh-cn/<namespace>.ts` is typed `TranslatedNamespace<typeof source>`, and the unit test
  checks key and placeholder parity. Interpolation (`interpolate`) and the namespace type come from
  `@caxri/protocol`, the only workspace package mobile production code may import besides the
  transport, so Desktop and mobile share one implementation.

## Dates and numbers

Format dates, times, and numbers in the interface language, not the system locale. A Chinese interface on an English
system should still date and group its figures the Chinese way, and the reverse.

- Use `localeDateTimeFormat`, `localeNumberFormat`, `formatCount`, and the `formatDateTime`, `formatDate`, and
  `formatTime` shortcuts from `apps/desktop/src/renderer/src/lib/locale-format.ts`. They read the active locale and
  cache their `Intl` formatters.
- Never call `toLocaleString`, `toLocaleDateString`, or `toLocaleTimeString`, and never build an `Intl` formatter with an
  `undefined` locale or a hard-coded `en-US`; ESLint rejects the bare forms in the Renderer.
- Store timestamps as numbers and format at render time. A label formatted when the record was written (a
  Notification's time, for example) stays in the language that was active then.
- Main formats durations through its own dictionary (`desktop.duration.*`), so a native banner such as
  `Finished in 2m 5s` renders as `已完成，用时 2 分 5 秒`.

## What stays untranslated

- Product and vendor names: Caxri, Claude, Codex, Grok, GitHub, macOS.
- Identifiers the user types or matches: command ids, setting keys, file paths, Git refs, shell
  commands, keyboard shortcut glyphs.
- Agent prompts, Agent transcripts, Terminal output, log and diagnostic text, and anything sent to
  the Server or an Agent.
- The code editor's built-in interface (Monaco's find widget, context menu, and command strings) and the output of
  the `caxri` CLI, which prints English regardless of `workbench.language`.
- Text inside tests and E2E selectors. E2E launches pass Chromium `--lang=en-US`, so the default
  `workbench.language` resolves to English on any host.

Suspend is the automatic memory-saving park of a background Agent (and the Process Explorer action that does the
same by hand); it is never rendered as Pause or 暂停, which belong to progress and recovery states. Copy that points
at a setting builds its `Settings › Category` path from the category's translation (`settingCategoryPath`) rather than
spelling it by hand.

Follow macOS and VS Code Simplified Chinese conventions for everything else: full-width
punctuation (`，。：？！（）`) inside Chinese sentences, a space between Chinese and adjacent Latin
words or numbers, and `…` for an ellipsis.
