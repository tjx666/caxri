# Git diff review comments

Desktop Git diff tabs support Session-scoped comments on either comparison side. Each anchor is isolated by diff source (working tree, pull request, or commit SHA) and file path. Binary and patch-only views do not offer line comments because their display rows are not source-file line numbers. In a single-file or Open Changes diff, hover a line's gutter and click `+`, select lines and use **Add Review Comment** from the editor context menu or Command Palette, or press `Cmd+Shift+M` (a default keybinding for `editor.addReviewComment`, rebindable in Settings like any other command). The card under the selected line accepts `Cmd+Enter` to save and `Escape` to cancel. Comments can be edited or deleted in place. Editing a **sent** or **outdated** comment's text returns it to **pending**, so a correction is sendable again instead of being silently excluded.

The Command Palette also offers **Go to Next Review Comment** and **Go to Previous Review Comment** (only while the active tab is a Git diff with at least one mounted review comment), which jump across every file and side of that diff in path, then line, then side order, remembering where the last jump in that Session + repository left off; and **Show Pending Review Comments**, which opens the first repository with a pending comment (across every Session) and moves on to the next one on a repeat invocation once the first is cleared.

The diff tab badge counts pending comments for the current repository. The Git diff tab's own action rail (next to Diff View Options, alongside Previous/Next Change and Open Current File) carries the same count: a **Send N comment(s) to Agent** icon button appears only while at least one comment is pending for that repository, and a **Clear sent and outdated** icon button appears only once a comment has been sent or gone outdated. Send opens a dialog that previews one prompt containing each file reference, diff source, comparison side, captured code snippet, and comment; nothing goes to the Terminal before the reviewer confirms in that dialog. The target is the running Agent Terminal selected by the same visible-then-recent Session rule as file references. The Terminal receives the prompt as one bracketed paste and a submit key. Large prompts use the existing local long-paste file route. A review send requires a managed Agent launch and is rejected if that launch has exited, so it cannot submit into the shell. A failure (no running Agent Terminal, comments too long to send at once, or a Terminal write that did not complete) renders inline in the send dialog rather than as a toast, keeps the dialog open, and re-enables Send; every comment stays pending. A successful send marks the sent comments and excludes them from later sends.

Each anchor records its original line span and snippet. When refreshed diff content no longer matches that span, a pending comment becomes **outdated** and is excluded from sending; it is never moved to another line automatically. Clear sent and outdated removes those resolved cards from the tab. Comment cards remain visible when a multi-file row is virtualized out of view and then mounted again.

## Ownership and storage

Review comments are Server-owned, in-memory state scoped by Session + repository, not Renderer state: `GitReviewCommentStore` (`apps/server/src/domains/git-review/comments.ts`) holds every comment and emits a content-free `gitReview.changed` event (Session + repository identity only, never comment text) whenever a scope's comments change. This mirrors `projectStatus.changed`/`sessionPullRequests.changed`: a transient event, not a durable one replayed on reconnect, because a restart may have already lost the underlying data it would be replaying. The Desktop Renderer owns no comment state of its own; it reads through React Query (`gitReview.list`, `gitReview.pending`) and mutates through the public `gitReview.*` methods (add/edit/remove/refresh/clearResolved/send), so Renderer reload and closing/reopening a diff tab keep every comment. The protocol contract carries no Renderer-only concept, so a future mobile client reading through the gateway can share the same store instead of needing its own.

The store is deliberately **not durable**: it is held in memory only, with no SQLite table and no schema migration. **An app or Server restart loses every pending review comment.** Before quitting, if any repository has a pending comment, Desktop shows a separate confirmation ("Quit with pending review comments?", `apps/desktop/src/main/app-quit.ts`) alongside the existing running-task prompt; picking Quit Anyway discards them, and the read itself fails open (a Server that cannot be reached during quit does not block quitting on a reminder about data that loss may already have destroyed). The same pending count is reachable at any time through **Show Pending Review Comments** without waiting for quit.

## Protocol

`packages/protocol/src/domain/git-review-contract.ts` defines the schema, the shared pure helpers (anchor snippet extraction, prompt formatting, Terminal paste framing, the inline-vs-long-paste size boundary), and the `gitReview.*` method catalog:

- `gitReview.list` / `gitReview.pending`: reads.
- `gitReview.add` / `gitReview.edit` / `gitReview.remove` / `gitReview.refresh` / `gitReview.clearResolved`: CRUD and outdated-status recomputation.
- `gitReview.send`: builds the prompt from the Server's own store and performs the Terminal write.

Every write and control method is classified `memory` recovery in `effectfulCommandRecovery` (`packages/protocol/src/registry/method-types.ts`): a lost connection cannot re-apply it against durable state, because there is none.

## Send path

Building the prompt and writing it to the Terminal both happen on the Server (`apps/server/src/domains/git-review/send.ts`), not the Renderer: `gitReview.send` reads the pending, non-empty comments for a Session + repository from the store, resolves the repository root through `GitService.repositoryIdentity`, and reuses the same managed-Agent guard `terminal.input` already enforces (`terminals.agentLaunchId`/`writeAgentExact`) so a submission cannot land after its Agent launch has exited. The Renderer still owns everything the Server has no view of (Terminal selection (the same visible-then-recent Session rule used elsewhere), activation, and waiting for the Terminal to attach) and passes the resolved `terminalId` into `gitReview.send` (`git-review-send-commands.ts`). Large prompts route through the existing `LongPasteService` the same way an oversized Terminal paste does.

## Renderer surfaces

`git-review-comments.ts` re-exports the shared pure helpers from the protocol package. `git-review-comment-commands.ts` holds the Server-mutation wrappers (`caxri.request('gitReview.*', ...)`); `git-review-comment-binding.ts` mounts Monaco view zones for both diff sides and the single-sided added/deleted editor, keeps each zone's height matched to its card's rendered height, and subscribes to `gitReview.list` through `subscribeCaxriQuery` (`queries/client.ts`), a `QueryObserver`-based subscription for this kind of imperative, non-component Monaco integration code, mirroring `useCaxriQuery`'s own cache-key and staleness behavior. Each mounted editor also registers itself in a small in-memory registry so `git-review-navigation-commands.ts` can jump across every currently mounted editor's comments; a comment belonging to a file virtualized out of a multi-file "Open Changes" diff is not reachable by Next/Previous until it is mounted again. `git-review-send.tsx` renders the Send and Clear actions plus the preview dialog, and is mounted from the Git diff tab's action rail (`editor-tab-actions.tsx`) rather than as an overlay on the diff surface.
