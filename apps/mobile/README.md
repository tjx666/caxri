# Caxri Mobile

The Expo SDK 57 development client for Caxri's paired Agent Session companion.

The [Conversation guide](../../docs/mobile/CONVERSATION.md) describes the authorized Agent timeline,
native rendering, live updates, and Terminal fallback.
The [Changes guide](../../docs/mobile/CHANGES.md) describes authorized Git snapshots, bounded diffs,
live refresh, and the commit draft boundary.
The [APK size guide](../../docs/mobile/APK-SIZE.md) records internal Android build variants,
measurement, and upgrade identity checks.

The current live Terminal implementation is Android-only. iOS displays an explicit unavailable
state for that segment, including Conversation fallback; building the iOS app does not establish
live Terminal support. Cross-platform Terminal support remains a product target, not a verified
capability of this build.

## Local development

Run commands from the repository root:

```sh
bun run --cwd apps/mobile prebuild:android
bun run --cwd apps/mobile android
bun run --cwd apps/mobile dev
```

`android/` and `ios/` are generated by Expo Continuous Native Generation and stay untracked. A
local development build does not require an Expo or EAS account.

## Internal Android APK

`app.config.ts` owns the launcher icon, app version, and Android `versionCode`; keep its version in
sync with `package.json`. Regenerate the ignored native project after changing any of these values,
then build the release APK:

```sh
bun run --cwd apps/mobile prebuild:android -- --clean
bun run --cwd apps/mobile android -- --build-only --variant release
```

The APK is written to `apps/mobile/android/app/build/outputs/apk/release/app-release.apk`. This
release variant currently uses the generated debug keystore and is for internal testing. Before an
in-place upgrade, verify the APK package, `versionCode`, and signing certificate against the
installed build; then use `adb -s <serial> install -r <apk-path>` and inspect the launcher icon on
the device. If the signing certificate differs, stop instead of uninstalling or clearing app data.

The Android build requires JDK 17 and the SDK under `~/Library/Android/sdk`. It accepts an explicit
JDK 17 from `JAVA_HOME` or reuses an existing Gradle-managed JDK 17; newer Android Studio preview
JBRs are rejected because AGP 8.12's Prefab process can treat their native-access warning as a build
failure. Install **SDK Platform** `36`, **SDK Build Tools** `35.0.0` and `36.0.0`, **CMake**
`3.22.1`, and the exact **NDK (Side by side)** version declared by the current React Native package;
for React Native 0.86.3 that is `27.1.12297006`. Expo's library modules use Android Gradle Plugin
8.12's `35.0.0` default while the app module explicitly uses React Native's `36.0.0`. The build
preflight checks the complete toolchain and exits before Gradle starts when one item is missing, so
it never downloads or changes the Android toolchain as a side effect.

The iOS build requires the full Xcode application to be selected with `xcode-select` and an existing
CocoaPods installation. Build a chosen simulator without starting a second Metro process:

```sh
bun run --cwd apps/mobile ios -- --device <simulator-udid> --no-bundler
```

The `expo-constants` dependency deliberately uses an `npm:` alias. With the repository's pnpm 12
toolchain, a plain semver entry resolves the package without its required `expo` and `react-native`
peer context, producing a broken direct symlink even though transitive copies are valid. Remove the
alias only after `pnpm peers check` and Expo Doctor both pass with a plain entry.

`react-native-reanimated` stays at `4.5.1` while Expo 57's module core accepts
`react-native-worklets` through `0.10.x`; this is the current compatible pair also exercised by T3
Code Mobile. Re-run `expo install --check` before changing either version.

## Explicit Android device selection

Every device helper requires `--serial`; it never guesses among connected devices:

```sh
bun run --cwd apps/mobile android:device inspect --serial 192.0.2.1:5555
bun run --cwd apps/mobile android:device semantics --serial emulator-5554
bun run --cwd apps/mobile android:device tap --serial emulator-5554 --check-id session-detail-back
```

Expo's native build command is the exception: its `--device` option expects the Android model name,
not the ADB serial. For example:

```sh
bun run --cwd apps/mobile android -- --device M2105K81AC --no-bundler --no-install
```

The semantic receipt first verifies that Caxri owns the foreground Activity, then emits only stable
resource identifiers and structural flags. It never emits visible text, accessibility descriptions,
Terminal output, Session names, source, paths, or credentials.

## Performance diagnostics

The development-client sampler force-stops and resumes the installed app without clearing its data.
It requires a stable readiness `testID` and emits only Android launch timings, frame counts, and the
requested identifier:

```sh
bun run --cwd apps/mobile android:performance \
  --serial emulator-5554 \
  --ready-check-id session-list
```

`readyCheckUpperBoundMs` includes UIAutomator capture time. Expo development-client startup and these
upper bounds are diagnostics, not release gates. The current baseline and release budgets live in
[`docs/mobile/PERFORMANCE.md`](../../docs/mobile/PERFORMANCE.md).

## Tests and Android acceptance

Pure protocol, parsing, state, and policy logic stays in Vitest. The critical native workflow uses a
fake Agent with the real Desktop, Server Core, encrypted gateway, Android app, and PTY input path. It
is skipped unless one explicit ADB serial is provided:

```sh
CAXRI_MOBILE_ACCEPTANCE_SERIAL=emulator-5554 \
  bun run test:e2e:mobile:android
```

The guarded command accepts only a disposable Android emulator. It builds Desktop, regenerates the
native Android project from the current Expo configuration, creates the current release APK without
letting Expo select a device, and installs it through ADB on the exact serial. It clears app data
before and after the run, verifies that the package is non-debuggable, then pairs a fresh isolated
profile and sends one fixed short reply. It verifies that the waiting generation changes, disables
access, clears logcat, stops the isolated processes, and removes its temporary profile. It does not
depend on an ambient Metro server, a stale generated native project, or a previously installed
bundle. Pairing links are never attached to the test report.

The mobile app reconnects through the eligible IPv4 addresses captured during pairing. A Tailscale
address remains usable when the Mac changes Wi-Fi networks. Without Tailscale, if the Mac receives
new LAN addresses, use **Forget** in the mobile app and pair again from Desktop Settings. Automatic
local discovery is not supported.
