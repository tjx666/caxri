# Diagnostic privacy, log contracts, and GPU recovery

Structured logs carry timestamp, process, level, event, correlation ID, duration, and the build's application version and commit when known. Diagnostics contain application/runtime versions, redacted metadata/state, counts, and timing summaries. Home paths normalize to `$HOME`; secret-like keys, bearer/API tokens, GitHub tokens, and Slack tokens are redacted. Bundles never include file contents, terminal output/snapshots, environment values, prompts/responses, or agent transcripts.

Structured event names are owned by the browser-safe protocol `logEventCatalog`; production log sinks accept only its derived `LogEventName`, and the `logs.query.event` filter uses the same schema. Query results deliberately keep a bounded string event so older or externally produced JSONL records remain readable without weakening production write-time typing.

Diagnostics are held to two standards at once: a record must explain a specific failure after it happened, and the record set must measure behavior well enough to surface a problem nobody reported yet. Three call-site defects break the second standard while appearing to satisfy the first. An event that names an outcome but not its cause (a signal "ignored", a request "skipped") reads identically to a lost event, so any such outcome carries a closed reason enum rather than a bare boolean. A high-frequency event that is deduplicated or sampled to bound log volume can no longer answer "how many", so it is paired with one aggregate record per owning lifetime (launch, session, connection) carrying counts by outcome, counts by fixed enum member, and the slowest observed handling. State that only reaches the Renderer as an event leaves no local timeline, so a health or authority transition is logged with its `from` and `to` values whenever it changes. Aggregates use flat, fixed-vocabulary field names derived from the closed enum they count, because log records cannot nest and a bounded field space keeps a summary analyzable with `jq` alone. Metrics stay coarse under the fixed `owner`/`phase`/`outcome` labels of ADR 0008; the per-event detail belongs in the log record, never in a dynamic metric label.

Routine success on a hot path belongs in bounded in-memory metrics, not one file record per operation. Runtime log sinks
default to `debug`, retain three rotated generations per process, and are shared by every subsystem, so merely lowering a
chatty operation from `info` to `debug` still evicts the low-volume lifecycle evidence that incidents actually need.
Failure paths keep their full `info`/`warn` records and timings.

Expected Extension Host request cancellation and generation turnover are counted by the fixed
`extension_host.request` metric outcomes without writing `extension_host.error`; provider failures and uncorroborated
extension-thrown codes remain durable warnings. Normal PTY throughput uses the fixed `pty.throughput` aggregate and a
single lifetime summary. Dropped bytes keep a `pty.throughput` warning: the first drop in a lifetime is written at once,
later drops fold into at most one warning per minute carrying `droppedBytes` and `droppedWindows` since the previous
one, and the lifetime summary totals both.

External status commands (`gh`, `vc`, `linear`) write no per-call record on success. Each failure keeps its own
`project_status.cli` or `session_pull_requests.cli` record with a closed `failureReason`, and one
`<event>_summary` record per command operation per minute carries call, success, and failure counts, the
failure-reason distribution, and total and maximum durations.

Successful `logs.query` reads are not written to either Server Core request-log boundary. A cursor-following reader
consumes those same files, so recording its own success would continuously advance the cursor and turn the configured
poll into a self-sustaining request loop. Control queue metrics still measure the request, and failures remain logged at
both boundaries. The fixed `logs.query_latency` aggregate preserves successful request counts and duration without
writing another record into the queried source. Query results collapse identical content IDs across live and rotated
files before cursoring; the Renderer folds the same ID at most once per page as a defensive boundary. This prevents an
exit-flush duplicate from producing repeated React keys and a second feedback loop through `renderer.console_error`.

GPU failures form one Main-owned correlated incident. Main decodes Electron's raw POSIX child status into the Chromium result code, records selected window state and GPU command-line switches, then captures bounded hardware, ANGLE, Skia/Graphite, and feature status after `gpu-info-update`. The workbench Renderer may report only a strict browser-safe diagnostic union: Terminal renderer status with opaque Terminal identity, renderer enums and counters, process/focus/visibility booleans; the session GPU incident budget transition with its closed cause and counts; the content-free resize burst summary defined above; the fixed-schema Renderer performance receipt; or an OSC 52 clipboard write failure reduced to a closed error category, permission-query outcome, secure-context state, focus/visibility state, and user-activation booleans. These branches never admit Terminal output, clipboard content or size, prompts, DOM text, error names or messages, stack traces, source, paths, or environment data. Renderer reports immediately before or after a GPU exit are linked through the incident correlation window so post-mortem triage can distinguish a native GPU process loss from a stale xterm atlas or an input-focus failure. An incident may fall affected Terminals back to DOM rendering for the current session, but it never changes the next-launch hardware-acceleration setting; turning hardware acceleration off for later launches requires an explicit user action that passed the shared confirmation modal first, and the Renderer's `gpu.restartInSafeMode` request is sent only from that confirmed branch.

An enabled Terminal that falls back to DOM may retry WebGL at most three times within a rolling 60-second window, with jittered exponential backoff (1 s base, doubling, ±50% jitter, 60 s cap) so panes that lost the same GPU process do not rebuild their contexts in the same instant. Retries wait until the mounted pane and document are visible, stop permanently for that mount after the budget is exhausted, and are cancelled by disposal or a renderer-preference change. Because every pane is rebuilt on each tab switch, a per-mount budget alone cannot converge: a Renderer-session GPU incident budget counts distinct Main-correlated `gpu.recoveryRequested` incidents and, after three, pins every current and later-mounted Terminal to DOM with the closed reason `context-loss-limit`; the trigger is `gpu-incident-limit` when the pin ends an in-flight retry sequence (including one already exhausted on an already-DOM pane), and `preference-change`, `webgl-context-loss`, or `gpu-process-recovery` when a pane resolves under an already-pinned budget. The `on` preference pins only on Main-observed incidents; `auto` additionally pins after three context-loss episodes (losses within 2 s count as one episode, since one GPU event drops every pane's context), which covers contexts Chromium evicts without a GPU process exit. Every controller must be constructed with the session policy; there is no default that never pins. A pinned pane still publishes `visibility-restore` (with the closed reason) so Main can count restores after the pin, and an `unsupported` pane re-probes WebGL2 on visibility restore, activating with `webgl-reprobe-succeeded` once the GPU process is back. The budget caches only a positive WebGL2 probe per incident so a negative observed during the GPU restart gap is re-probed, is never persisted across launches, and resets only when the applied GPU acceleration preference actually changes or the user confirms a manual GPU retry; each pin and reset is reported once as a session-level `gpu-incident-budget` diagnostic (transition, closed cause, counts, Main correlation) that Main logs as `gpu.session_budget`. Terminal visibility restores are frame-scheduled: the focus, visibilitychange, and pageshow events of one window restore merge into one restore per pane, panes of a split run on consecutive frames in mount order, and the Renderer-lifetime count of merged events travels with every Terminal renderer diagnostic. Each retry sequence carries one content-free UUID plus its state, attempt count, limit, and next delay through the strict Renderer diagnostic union. A Main-owned GPU incident correlation remains attached across the delayed sequence, allowing diagnostics to distinguish scheduled, deferred, attempted, succeeded, failed, exhausted, cancelled, and budget-limited recovery without admitting arbitrary messages or user content. The `gpu.process_gone` record always carries the correlation-window counts (diagnostics, Terminals, WebGL creations, visibility restores) plus `relatedRendererSaturation`, which reads `buffer-limit` when the 32-entry Renderer diagnostic ring buffer evicted a diagnostic that would still fall inside the window, so the counts are lower bounds rather than exact.

Every `renderer.terminal_renderer_status` record also answers why a context was lost. The Renderer reports `liveWebglContextCount`, the Terminal WebGL contexts held across the window's panes, counted by the session policy and sampled before the lost context is released on a `webgl-context-loss` or `gpu-process-recovery` record. Main stamps what the Renderer cannot see: `msSinceGpuProcessGone` and the lifetime `gpuProcessGoneCount` from `child-process-gone`, plus `msSinceSystemResume`, `msSinceScreenUnlock`, and the lifetime `systemResumeCount` from `powerMonitor` (`gpu.process_gone` carries the wake fields too). Elapsed fields are `null` when the event never happened in this launch. xterm reports a loss about 3 s after Chromium drops the context (it waits for a `webglcontextrestored` that never comes), so read the elapsed values with that offset. A loss within a few seconds of a GPU process exit is a GPU process reset; a loss at or above 16 live contexts with no GPU exit is Chromium's per-process live-context cap evicting the oldest context; a loss shortly after a resume or unlock with neither is a sleep or display change. During a GPU process reset each pane samples the count after earlier panes released theirs, so take the maximum across the burst.

The status-bar DOM chip offers a confirmed manual GPU retry for settled failures, including unsupported WebGL2 and the session incident limit. It resets the window's incident budget and capability probe cache with the closed cause `manual-retry`, then makes one immediate attempt for the original mounted Terminal. It does not change settings, restart the PTY or Agent, or rebuild other mounted panes. Failed attempts remain on DOM and report a user-facing error without scheduling another automatic sequence. Later context losses retain the normal bounded retry policy. In-progress automatic retries remain informational, and confirmation is ignored if its originating pane has been disposed or replaced.

The application version and short commit hash are injected at build time and read once by Desktop Main, which stamps its own logs and forwards them to the Server Core's environment so both processes' logs and the diagnostics export can be correlated to the exact build.

Desktop Main, Server Core, Terminal Host, and Extension Host JSONL files live together beneath the
active runtime profile's `logs/` directory. Development, worktree, E2E, Acceptance, and packaged
launches therefore keep diagnostics attached to the same isolated userData identity as SQLite and
Server state.

CLI `logs follow` resets to a 250 ms poll after output and exponentially backs off idle polling to a
two-second ceiling, avoiding repeated suffix reads and parsing when no new records exist.
