# Git repositories, worktrees, and Project Status

Git operations run via `execFile('git', argv)` with fixed argv constructors and a filtered environment. The Renderer can request only fixed, structured repository mutations: switching to an existing local branch (Server Core resolves the opaque approved repository ID, re-lists its bounded local refs, and invokes `git switch -- <branch>` only after an exact match), discarding confirmed working-tree changes, and Sync Changes (`git pull`, then `git push`). There is no arbitrary checkout, fetch, reset, or command surface. One Server Core-wide semaphore admits at most eight Git subprocesses, metadata commands cap output at 4 MiB, and bounded file-diff commands retain the configured file-size cap. A shared Server Core resolver checks the GUI PATH, then reads a bounded marker-delimited PATH and environment snapshot from the interactive login shell; it caches validated absolute executables and revalidates stale entries. Agent adapters, Agent PTYs, version probes, and the fixed Project Status allowlist (`gh`, `vc`, `linear`) use this resolver. Server commands (Git, version probes, Project Status CLIs) take only its filtered environment plus the login-shell PATH, because startup-file variables such as `LANG` or `GIT_*` could change output Caxri parses; Agent processes additionally inherit the rest of the interactive login-shell environment (see the Terminal lifecycle reference). Claude Code integration reads only compact live-session metadata: at most 512 candidates, eight reads at once, and no more than 128 KiB from any file. Codex integration locates state beneath the documented `CODEX_HOME`/`CODEX_SQLITE_HOME` roots and queries at most 32 capability-detected thread indexes read-only. Ordinary Agent probes never open transcripts. Available title, session ID, activity, and usage metadata are correlated with the persisted cwd of the matching provider Terminal. A provider-owned Agent session ID may be claimed by only one Terminal; unbound probes exclude IDs already claimed by another Terminal and IDs discarded by a restart. Every new Session starts with the automatic sidebar title `Untitled`, while its first Terminal keeps the provider-specific `Shell`, `Claude Code`, or `Codex` title. A probe without a verified provider title leaves that default in place, because the sidebar row already shows the provider icon; only a native notification, which has no icon, substitutes the content-free `Claude Code session` or `Codex session` derived from the Terminal's provider alone. Naming and rename both treat the default as an absent title rather than as a current name. The first Agent Terminal becomes the Session's primary Agent Terminal and exclusively owns later automatic sidebar-title promotion from useful metadata; later Agent Terminals retain independent metadata without replacing it. Manual rename is serialized per Caxri Session and targets that exact primary binding. Codex 0.110.0+ within major 0 uses the bounded App Server `thread/name/set` method, and Claude Code 2.1.232+ within major 2 uses a bounded non-interactive `/rename`; older, unknown-major, or unverifiable versions fail closed, and Caxri never writes provider-private persistence or injects text into the live PTY. Provider success precedes one SQLite transaction that commits the provider-returned title, the changefeed entry, and the durable command receipt together. A crash before that transaction can idempotently repeat the same provider rename; after commit, replay returns the stored result without another provider call. The provider's durable resume name changes immediately, but an already-running TUI may retain its cached heading until the next resume because the one-shot sidecar cannot publish into that process. A manual title remains stable across Agent metadata refresh, restart, and primary-Terminal succession. Closing the primary promotes the next Agent Terminal. Missing or changed storage produces `unknown`; it never interrupts PTY input/output or resets a known Session title.

The Source Control and Project Status views list only the active Workbench Root repository and its initialized submodules or nested repositories. Other linked worktrees and their children remain outside that summary, even when authorized; the Workbench Root picker owns switching between them. The Working Tree view uses the current index and filesystem, while its lazy Pull Request view asks `gh pr view` for the current branch's validated base/head object IDs and diffs that committed range without mixing in local working-tree changes. The same Server projection counts commits reachable from local HEAD but absent from the validated pull request head; Source Control renders that value as the pull request's unpushed count instead of reusing tracking-upstream `ahead`, which may describe a different ref. Repository discovery uses structured Git output, coalesces concurrent summaries, and passes an opaque repository ID back for diff requests. `git.diffDocument` returns bounded original and working-tree text for Monaco without exposing an arbitrary Git command or weakening repository containment. Nested roots inherit the containing Workbench Project grant. A linked worktree outside that root becomes eligible for selection after an explicit Continue action, a native folder-picker grant, or the user's `continueAutomatically` policy authorizes its exact canonical path as a Project; Git discovery alone never expands durable path authority. While a Session is still bound to the main worktree, the picker leads with the worktrees the Session's own Agent conversation named; that ranking is a filter over what Git topology already reported and never introduces, authorizes, or widens a root. See `docs/session-conversation-context.md`. The optional `git.fileHead` projection resolves an Editor path inside Server Core and returns its latest touching commit together with that opaque repository ID and repository-relative path, so Editor title actions never duplicate nested-repository path ownership in the Renderer.

Automatic worktree attribution has no CLI, Agent Endpoint, or installed-skill dependency. The launch baseline binds the owning repository and exact Terminal generation. For a locally classified `git worktree add`, the authenticated `shellToolStarted` signal blocks tool execution until Server Core captures a bounded forced topology read; the outcome must carry the same opaque tool-use id, after which Server Core forces one more topology read. Claude failure consumes the pair immediately. Codex does not expose a reliable success discriminator, so a completed outcome proves success only when exactly one linked worktree was added between the paired snapshots. Any overlapping classified windows in one repository are ambiguous even when their outcomes land in different batches; their bounded reservations stay inert until each outcome or TTL consumes them. Capacity overflow temporarily makes all creation attribution fail closed instead of growing the serialized queue. Multiple additions inside one paired window are also ambiguous. A missing or stale launch, missing pair, timeout, failed Git read, pre-existing path, or topology alone also fails closed without a prompt, selection, or Project authorization. Both unique creation attribution and a verified Agent working-directory divergence use one following policy: `ask` prompts, `continueWhenAuthorized` selects existing Projects and prompts for unknown roots, `ignore` does neither, and `continueAutomatically` registers and selects proven roots without prompting. The default remains `ask`. Automatic following rechecks policy, provenance, Session binding, repository topology and root identity before committing registration and selection without another asynchronous gap. The Agent-writable `settings.patch` contract cannot enable `continueAutomatically`; the user settings surface owns this standing authorization. Main still accepts only the opaque candidate ID for manual Continue, and Server Core revalidates that candidate before registration.

Archiving a Session can also remove its worktree when the user enables `workbench.removeWorktreeOnArchive` (off by default; the archive cleanup follows Lody's). Only a linked worktree Caxri registered on the Session's own Project's behalf qualifies, never a main checkout or a folder added as its own Project, and only while no unarchived Session still works in it. Server Core decides before the archive, because the Session pull request owner stops tracking archived Sessions: a merged pull request removes the worktree without asking, while any other state needs the user's `remove` answer from Main's native archive confirmation (`session.confirmArchiveWorktree`). Non-interactive archives (pull request settlement, CLI, Agent, and bot) pass no answer and therefore remove only merged worktrees. `ArchivedWorktreeCleanup` (`apps/server/src/domains/workbench/archive-worktree.ts`) waits ten seconds so the archive notice's Undo keeps the worktree, re-proves every condition, commits non-ignored uncommitted changes to the worktree's branch with hooks and signing disabled, refuses a detached HEAD or a half-finished merge, cherry-pick, or revert, runs `git worktree remove --force` from the owner checkout, keeps the branch, and silently rebinds every Session bound to the removed root to its own Project. Each outcome is one `workbench_root.worktree_archive_cleanup` event with a closed skip reason and no path or branch.

Each approved Git scope also exposes lazy, independently pageable commit history through its opaque repository ID. Server Core parses fixed NUL-delimited `git log` fields, caps page size and offset, and accepts only an existing, non-symlink path contained by that repository for optional subtree history. Selecting a commit issues a separate read-only metadata/file-list request; merge commits compare through their first-parent history, file results are bounded, and no history request exposes checkout, reset, fetch, or another mutation.

The bundled Project Status extension activates when its declared badge is queried or its ViewContainer opens. Its badge provider and TreeDataProvider ask Server Core, through the public capability-scoped `caxri` API, to combine the approved primary repository and initialized submodules with GitHub PR/check data, deliberate Linear references from the PR body, LobeHub acceptance reports linked from the PR body, and Vercel deployments. The always-visible Status Bar uses a separate lightweight primary-repository overview: it reads Git changes plus the origin and current GitHub PR, never triggering Vercel, and file events refresh only `git.summary`. It also names the Linear issue the branch is delivering, from the PR body it already fetched, the branch name, or this Session's own Agent conversation; bare markers from the latter two are admitted only when the team key matches the workspace's own key list, and only the leading issue is resolved. See `docs/session-conversation-context.md`. Its branch picker lazily lists the approved primary repository's local refs and uses the narrow switch operation above; its additions/deletions are the tracked working-tree diff against `HEAD`, while untracked files remain visible in Source Control without synthetic line counts. Server Core invokes `gh`, `lh`, `linear`, and `vc` only through structured argv arrays, filtered environment inheritance, timeouts, and bounded output; Renderer receives validated read models and never CLI access. Every one of those invocations passes through a single external-status hub (`apps/server/src/domains/external-status/`): one GitHub pull-request record per `owner/repo#number` is shared by the Status panel, the Status Bar overview, the sidebar delivery badges, and Source Control's pull-request diff, and one circuit breaker per source pauses that source until the reset GitHub reports, persisting the pause under `~/.cache/caxri/` so parallel worktree Servers observe it too. A failed refresh always backs off further than a successful one, and a reserve of GraphQL points is left unspent so the user's own `gh` calls keep working. See `docs/external-status-quota.md`. Tree tooltips cross the Extension Host boundary as either bounded plain text or bounded structured rows; structured URLs admit credential-free HTTP(S) only, render through an interactive Renderer hover card, and still use Main's trusted-origin policy. Missing tools, authentication, links, rate limits, and timeouts stay scoped to the relevant surface.

Extension views opt into numeric activity with manifest `badge: true` and
`views.registerViewBadgeProvider`. The read-only `badge.snapshot` operation shares view activation,
request cancellation, generation fences, and Session/Workbench Root authority with content reads.
Source Control and badge registrations have independent roles on the same view; unload retires both.
Providers emit scoped `badge` invalidation events, never ambient pushes of cached counts. Renderer
queries declared providers before their tabs open, keys results by view/generation/Workbench scope,
and aggregates counts and descriptions onto each owning container. Error, crashed, and disabled
providers contribute no badge. Concurrent activation is coalesced per extension generation. Git
uses the cached full `changedFileCount` summary; Status owns failure aggregation in its extension.

Git diff visibility is independent of file-tree visibility and Git tracking. The bundled Git extension applies
`git.diffExclude` to repository-relative paths when projecting Working Tree, Commit, and Pull Request changes;
Server summaries retain their complete status semantics. A revision-bound, provider-owned header action toggles
temporary visibility within the Source Control scope. Generic Source Control chrome renders optional header
actions without interpreting Git command IDs. Aggregate diff tabs carry only a boolean visibility override and
apply the same shared glob matcher to their fresh data. Hidden changes remain included in total counts and are
identified explicitly; bulk discard is unavailable until hidden changes are revealed.

Delivery check states are shared by the protocol and public Extension API. GitHub cancellation
remains `cancelled` through Server parsing, Extension tree projection, and Session PR summaries;
it is neither a passing check nor a delivery failure. See
[delivery-status semantics](../../../../docs/external-status-quota.md#cancelled-github-checks).

Project Status keeps PR `lifecycle` (open, draft, merged, closed) separate from `state` (the CI
rollup). Its PR row uses the lifecycle icon, including the theme's purple `merged` token, while
the row description, tooltip, check children, and failure badge retain the independent CI result.
The Session sidebar reuses the same Server projection. Missing provider lifecycle stays unknown;
successful checks never imply an open or merged PR.

Project Status branch publication is Server-owned evidence, carried by the typed Project Status
contract and rendered by the bundled Status extension. It compares a captured local commit with
the same-named GitHub branch on origin through the existing external-status quota hub. Local
tracking refs invalidate cached evidence but never establish publication. See
[external status governance](../../../../docs/external-status-quota.md#branch-publication-in-project-status)
for freshness, unsupported origins, and incomplete-history behavior.
